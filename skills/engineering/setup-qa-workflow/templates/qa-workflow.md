# 研发与浏览器真机测试闭环工作流 (QA & Browser Testing Workflow)

本规范定义了结合 **Matt Pocock 软件工程技能体系** 与 **`qa-test-planner` + 真实浏览器自动化工具** 的端到端闭环开发与验收流水线。

> 模板说明：本文件由 `/setup-qa-workflow` 生成。`{DEV_COMMAND}`、`{WEB_PORT}`、`{E2E_COMMAND}`、`{E2E_DIR}`、`{CORE_LINKS}` 为生成时已确认的项目参数；后续项目结构变化时直接编辑本文件，无需重跑技能。

---

## 一、核心闭环全景流程

```
[1. 需求与对齐]       /grill-with-docs ──> 厘清业务边界，更新 GLOSSARY.md / ADR
        │
        ▼
[2. 规格确立]         /to-spec ──────────> 生成 .scratch/<feature>/spec.md
        │
        ├───────────────────────────────────────┐
        ▼ (研发轨)                              ▼ (测试轨)
[3A. 任务拓扑拆解]   /to-tickets               [3B. 测试集规划]   /qa-test-planner
     生成 issues/*.md（条件触发）                  生成 .scratch/<feature>/qa-plan.md
        │                                           (含 P0 冒烟、关键定位器、断言)
        ▼                                       │
[4. 编码实现]        /implement (TDD)          │
     单测与集成测试绿灯 (Seam 契约保证)              │
        │                                       │
        ├───────────────────────────────────────┘
        ▼
[5. 真实浏览器验收]  执行 Agent 调用 ego-browser 逐条验收，Playwright 固化回归
                     逐条执行 qa-plan.md 中的用例：点击、输入、交互、截图
        │
        ├──────────── 若用例失败 (FAIL) ───> 捕获现场截图与 Console Error
        │                                   调用 diagnosing-bugs 定位并修复代码
        ▼ (全部 PASS)                       重新回到浏览器验证
[6. 双轴代码审查]    code-review ─────────> Standards 规范轴 + Spec 需求轴对账（交付前硬门禁）
        │
        ▼
[7. 交付与沉淀]      pr ──────────────────> 挂载浏览器真实操作的前后对比证据
                     /retro ──────────────> 会话复盘与环境优化
```

## 二、适用范围与剪裁

完整 7 阶段流程为**多会话、跨模块的特性开发**设计，请按改动规模剪裁，不要一刀切：

| 改动规模 | 适用流程 |
| --- | --- |
| 大型特性（多会话、跨模块、涉及核心链路） | 完整 7 阶段流程 |
| 中型改动（单会话可完成的独立功能） | 跳过 3A 工单拆解：`/to-spec` → `/qa-test-planner` → `/implement`（TDD）→ 浏览器验收 → `code-review` 双轴审查 → `/pr` |
| 小型修复（文案、样式、单点 Bug） | 直接 `/implement` + TDD；触及 P0 链路时补跑一次 P0 冒烟与 Standards 轴快速自查 |

**3A 触发条件（按协作形态而非规模决策）**：仅当预估**跨会话/跨人交接**，或计划用 `/implement-spec` 并发派发（其沿工单阻塞图推进 frontier）时，才执行 `/to-tickets` 拆出 `issues/` 碎文件；单会话冲刺直接从 `spec.md` 的 Work Orders 小节起 `/implement`，不产生 `issues/` 目录，避免碎文件与 spec 的多头同步摩擦。跨人交接时，工单状态与验收证据经 `docs/handoff/` 交接文档入库流转（`.scratch/` 为单机工作区，不出本机，详见 `issue-tracker.md`）。

**不可剪裁的红线**：只要改动触及用户可见的核心链路（{CORE_LINKS}），无论规模大小，阶段 5 的真实浏览器验收不可跳过。

**结果落盘**：浏览器验收结果（通过/失败、关键截图清单、Console 报错）以 `## 执行记录` 小节追加到 `.scratch/<feature>/qa-plan.md` 末尾；缺陷修复后的回归结果继续追加，形成完整证据链，供 `/pr` 阶段引用。截图统一存放 `.scratch/<feature>/screenshots/`，与 spec、qa-plan 同目录归档；`.scratch/` 已在 `.gitignore` 中，不会污染代码树，禁止散落到 `/tmp` 或源码目录。截图命名规范（编号与 qa-plan 用例编号一致）：
- 通过证据：`TC01-场景名.png`（如 `TC01-chat-stream-pass.png`）；
- 失败现场：`TC01-场景名-FAIL-YYYYMMDDHHmmss.png`，PR 合并前禁止覆盖或删除；修复回归的 `## 执行记录` 须同时引用 FAIL 现场图与 PASS 图，构成 Before/After 闭环证据链。

**成本控制（时间盒）**：交互式浏览器验收只跑本次改动直接影响的链路，默认不超过 **5 条用例 / 15 分钟**；已验收过的核心链路回归交给 Playwright 脚本（`{E2E_COMMAND}`，确定性执行、秒级完成、不耗模型 token），交互式浏览器只用于新行为的首次验收。超时或失败用例过多时，停下来排查或升级计划粒度，不要硬跑全量。

**无 qa-plan 时的验收**：若实现前未运行 `/qa-test-planner`（如小改动直接 `/implement`），验收前由 Agent 从 spec / 工单 / 改动摘要推导 3–5 条 P0 冒烟用例，写入 `.scratch/<feature>/qa-plan.md`（无该目录时附到 PR 描述），再执行阶段 5；不触及核心链路的小改动可只跑单测与 typecheck。注意 `/implement`、`/implement-spec` 技能本身不包含浏览器验收步骤，阶段 5 是本流程对主编排 Agent 的指令——跨会话执行 `/implement` 时，需确认该会话已知读本流程。

**流程自身的剪裁**：本文件每条强制规则都应能陈述它的捕获目标。`/retro` 复盘时，反复消耗轮次却从未捕获缺陷、从未改变决策的规则，必须提案删减或降级；底层模型能力跨代升级后，应重估全部防呆类约束的残余收益。

## 三、关键阶段执行规范

### 1. 需求对齐止损线（阶段 1）
- 当剩余未澄清问题已不会显著改变实现方向与验收标准时，即可进入下一阶段；边缘分支的取舍允许留到编码阶段按需决策，不追求前置规划覆盖所有细节。

### 2. 规格与测试规划阶段（阶段 2 & 3B）
- **触发时机**：在 `/to-spec` 产出技术规格后，立即触发 `/qa-test-planner`。
- **输出位置**：`.scratch/<feature>/qa-plan.md`。
- **QA Planner 规划原则**：
  1. **分级清晰**：标注 P0（核心阻断/Happy Path）、P1（重要分支与表单校验）、P2（边缘容错）。
  2. **自动化友好**：测试步骤中明确标注元素特征（如目标按钮文案 `text="立即提交"`、输入框标签 `placeholder="..."` 或语义化角色 `role="button"`）。
  3. **可量化预期断言**：避免“页面表现正常”等模糊描述，必须具体到“弹窗提示‘保存成功’且网络请求返回 200”。

### 3. 代码实现阶段（阶段 4）
- **驱动机制**：由 `/implement` 或 `/implement-spec` 驱动底层 `tdd` 技能，通过纯代码层面的单测保证内部状态和公共接口（Seams）符合设计。
- **单工单逐步推进 vs 批量冲刺模式（Batch Implementation）**：
  - **单工单模式（精细调试/排障）**：当指令显式指定单张工单（如 `/implement 工单 01`）时，Agent 完成该工单并确保单测全绿后，更新工单状态为 `done`（存在 `issues/` 工单文件时）并停下汇报，等待用户下一张工单指令。
  - **批量冲刺模式（消除流程摩擦，推荐）**：当用户传入 `/implement --all`、`/implement`（无工单参数，默认顺次承接全部 `ready-for-agent` 待办工单）、`/implement-spec`，或口头要求“连续实现/批量开工工单 01-NN”时，Agent 获得**连续冲刺授权**：
    1. **拓扑顺次执行**：依据工单依赖顺序，在同一会话中顺次执行各工单的 TDD 红绿实现；
    2. **自动状态流转**：每张工单通过后，内部自动将对应 issue 文件中的 `status: "ready-for-agent"` 改写为 `status: "done"`（未拆出 `issues/` 时跳过，以 spec 的 Work Orders 小节为进度依据）；
    3. **非阻断不停顿**：全流程不因单张工单完成而人为停顿询问“是否继续”，除非遭遇架构假设破裂、测试无法自愈或外部阻断；
    4. **收敛汇总交付**：全部工单编码与静态类型检查（`typecheck`）全绿后，一次性输出阶段 4 批量实现交付矩阵，并主动无缝流转至阶段 5（真实浏览器验收）。

### 4. 真实浏览器执行与验收阶段（阶段 5）
- **环境就绪（先探活，再开浏览器；三级自愈，全程无人值守）**：
  1. **探活**：先 `curl -s -o /dev/null -w "%{http_code}" http://localhost:{WEB_PORT}` 确认返回 200；未通则扫描端口漂移区间（以项目端口决议配置为准；无此类配置时探测首选端口起 +30 区间，禁止硬编码无依据的猜测端口）；
  2. **防伪绿**：对响应 200 的端口抓取首页确认预期应用锚点存在（漂移端口可能挂着旧会话的陈旧 dev server、跑着旧代码），无法确认时视为未就绪；
  3. **自愈拉起**：均不就绪时后台执行 `{DEV_COMMAND}`，以 1–2 秒间隔探针等待就绪，预算 60–90 秒覆盖冷启动与首编译；超时再升级人工介入。
  **禁止 kill 占用端口的任何进程**（可能是用户其他工作）；**禁止把连接拒绝（ERR_CONNECTION_REFUSED）判定为业务 Bug 进入 `diagnosing-bugs` 排查**。
- **就绪锚点（防 SSR 水合假死）**：SSR 页面「HTML 可见 ≠ React 事件已挂载」，水合完成前点击会出现"点击无效"假报警。操作前以「客户端就绪后才出现的元素」为锚点确认就绪（如核心交互页的输入框、页面主标题）。**禁止用 networkidle 作等待条件**——dev 模式的 HMR 与长连接会让网络永不空闲。
- **定位器校准（防预估选择器假报警）**：qa-plan 规划于实现之前，定位器特征是预估值。进入浏览器执行前，对照阶段 4 实现的真实组件属性快速校准 qa-plan.md 中的定位器（选择器、文案、属性），存在合理微调时就地同步，避免因选择器字面微差导致超时假报警。**校准范围仅限「如何找到元素」**：预期行为与断言一律禁止改动——实现与 spec 文案不一致属于需求偏差，留至阶段 6 Spec 轴记录，不得靠改 qa-plan 迁就实现。每次校准须在 `## 执行记录` 留一行痕迹（用例编号、原定位器、校准后定位器）。
- **执行工具分级铁律（macOS 强制 `ego-browser` 可见窗口，严禁擅自降级）**：
  - **严防工具调用习惯性偏置 (Schema Bias 防线)**：由于 Playwright 往往作为 MCP 函数直接注入模型上下文，而 `ego-browser` 是命令行 CLI 工具，模型在推演下一步时极易产生偷懒偏置而滑向 Playwright。**在 macOS 桌面环境下，阶段 5 第一步必须执行命令行 `ego-browser --version` 进行探活；探活成功后必须且只能通过 `ego-browser` 唤起前台可视窗口执行验收，严禁未经探活直接调用 `mcp__playwright__*` 工具，未经探活擅自降级视为严重流程违规！**
  - **`ego-browser`（第一优先级，宿主支持时必须且唯一首选）**：在支持并安装了 `ego-browser` 的环境（如 macOS 桌面开发机）下，凡进行页面交互、UI 探索、缺陷排查或功能验收，**必须调用 `ego-browser`**（驱动 `ego-browser nodejs -e '...'` CLI 执行）：
    1. **真实登录态与个人上下文**：天然继承宿主真实浏览器的登录凭证、Cookie 与本地存储，免除 mock 匿名建号与反复登录阻断，直达真实业务场景；
    2. **人机协同与无缝接管**：在前台真实弹出可视 Chromium 窗口，人类可实时观测 Agent 的点击与交互轨迹，遇到卡点或人机验证时人类可随时无缝接管；
    3. **高吞吐更省 Token**：支持单脚本批处理执行多步连续操作（一个 turn 运行一组动作），避免每个细微点击都往返传输数千行超大 a11y 树，显著缩短往返耗时并大幅降低 Token 消耗。
  - **`Playwright`（第二优先级，严格受限的降级兜底 + 自动化回归代码固化）**：
    - **严格的降级触发条件**：只有且仅当通过命令行执行 `ego-browser --version` 报错、未安装 CLI、或显式处于无 GUI 的纯 CI/Linux 环境时，才允许经明确说明后降级使用 Playwright（包括 Playwright MCP 工具或原生 Playwright 驱动）完成阶段 5 的验收与截图落盘；
    - **静态脚本固化职责**：无论使用何种工具完成即时交互验收，验证通过的核心链路均应固化为无头 CI 自动化回归脚本代码（`{E2E_DIR}/*.spec.ts`，通过 `{E2E_COMMAND}` 执行），防御未来迭代劣化。现有 P0 固化用例：（初始为空，随首次验收在此沉淀登记清单）。打桩约定：外部上游一律拦截返回确定性数据；认证优先走真实链路并复用固定身份夹具（防匿名账号创建限流）。
- **异步链路终态验收**：diff 触及异步任务链路（提交后由后台消费者/上游服务异步完成）时，"提交成功"不算 PASS，必须验收至终态（成功或明确的失败态）。等待前先做健康检查（消费者进程在跑、上游凭证已配置），等待上限由 qa-plan 按链路给出；超时记 FAIL 进入 `diagnosing-bugs` 排查，禁止无限轮询；等待时间不计入交互验收时间盒。当且仅当断言涉及服务端状态时，附一条服务端证据（消费者日志 / 数据库记录 / 队列状态，三选一）。
- **异常自愈机制（Defect Remediation Loop）**：
  - 若在浏览器中遇到按钮点击无效、样式遮挡、控制台红字报错或断言不符：
  - 自动输出简明 Bug 记录（含报错日志与截图），交由 `diagnosing-bugs` 技能进行插桩排查与修复，修复后在浏览器重新回归。

### 5. 双轴代码审查阶段（阶段 6，交付前必经硬门禁）
- **不可剪裁的红线**：大型与中型改动，阶段 5（真机验收）通过后，严禁直接跃迁阶段 7（提交/交付），必须主动触发 `code-review` 技能，以批判性视角完成双轴对账：
  - **Standards 规范轴对账表**：安全无泄漏（密钥、凭证、隐私内容零入日志与事件）、移动端红线（热区 ≥44px、safe-area 适配）、框架与仓库工程规范、语言与注释规范。typecheck 与单测结论直接引用运行输出，不重复手填；
  - **Spec 需求轴对账表**：对照 `.scratch/<feature>/spec.md` 逐条核验全部 User Stories（核验动作不省略），输出允许聚合压缩：PASS 项可按工单/模块分组并以区间枚举编号（如 `US-01~04：PASS`），编号必须全部显式出现，禁止无编号的「全部通过」；偏差/未实现/降级项必须逐条独立列出并附说明；每组附至少一条证据指针（测试文件或截图）。**完整性校验：任何未出现在对账表中的 US 编号，该轴直接判 FAIL**——严防需求暗中缩水；警惕测试与代码同源、一起误解需求。
- **快车道豁免**：小型单点修复不强制双轴审查；触及 P0 核心链路时降级为 Standards 轴快速自查（不强制 Spec 轴对账表）。
- **发现三档分流（审查结论）**：本次修（琐碎且安全，当前 MR 内修掉）；转专项（动结构的清理，以 `## 遗留事项` 追加到 `.scratch/<feature>/qa-plan.md` 末尾，人工择机调用 `/improve-codebase-architecture` 独立处理，不搭功能 MR）；驳回（ADR 记载的有意设计，注明理由关闭，防重复报警）。**出具三档结论后方可解锁提交操作。**
- **审查-修复-复验回路**：「本次修」触及核心链路时，阶段 5 的既有验收证据对已改动行为失效，必须补跑对应浏览器用例并向 `qa-plan.md` 追加 `## 执行记录`，再解锁提交。

### 6. 人工终审与 PR 证据链（阶段 7）
- **人工终审顺序**：先对照 spec 核查验收标准与测试证据——重点判断"测试是否锁定了本次需求真正关心的行为"；再扫双轴审查的高危输出（未触及高危区则跳过）；常规代码信任单测与 typecheck，不逐行深读；
- 执行 `pr` 时，必须将浏览器中真实点击截取的成功操作图（Before/After 证据）作为 PR 描述的“证据附件”提交，并把 `## 遗留事项` 带入 PR 描述；不执行 `/pr` 则不做额外动作。
