## 技术栈适配（Next.js）

> 本章节由 `/setup-qa-workflow` 在检测到宿主项目依赖含 `next` 时并入生成的规范。只承载 Next.js 私有规则，通用流水线规则见核心规范正文。

### 阶段 5 补充规则（真实浏览器验收）

1. **水合锚点（防 SSR 假死）**：App Router 页面「HTML 可见 ≠ React 事件已挂载」。水合完成前点击会出现「点击无效」假报警。操作前以「客户端就绪后才可交互的元素」为锚点确认就绪（核心交互页的输入框、主按钮），不要以静态文本可见作为就绪信号。
2. **禁止 `networkidle` 等待条件**：dev 模式的 HMR WebSocket 与 RSC 长连接让网络永不空闲。等待条件一律用具体元素「可见/可交互」，不用网络空闲。
3. **dev 首编译预算**：App Router 按需编译，首个路由访问可能耗时 10–60 秒；探活返回 200 不代表页面可交互，探活后仍要等水合锚点。客户端路由跳转（`next/link`）同样按需编译目标路由，用例步骤间的等待预算要覆盖编译时间，避免把编译耗时误判为超时 FAIL。
4. **RSC 与客户端组件边界**：交互元素必须渲染在客户端组件（`'use client'`）中才可点击与断言交互行为；服务端组件输出的静态内容只做可见性断言。
5. **端口漂移惯例**：`next dev` 默认 3000；端口被占用时 Next 自动递增（3001…），因此漂移扫描区间（首选端口起 +30）天然覆盖该行为；仍以项目脚本（`-p` 参数或端口决议脚本）为权威来源。
6. **dev 与 build 行为差异**：`next dev` 与 `next build && next start` 行为可能不同（React Strict Mode 双渲染、缓存策略、流式 SSR 时序）。性能、缓存、时序类缺陷必须在 `start`（生产构建）模式下复验后才能定论。

### 阶段 4 补充规则（编码实现）

- 改动画到交互组件时确认其在客户端组件边界内；把交互写进 RSC 会在运行时才暴露，单测不一定能捕获。
- 涉及缓存（`fetch` 缓存、路由缓存、`revalidate`）的改动，验收用例需声明缓存前提，避免「上次的数据」造成假绿/假红。
